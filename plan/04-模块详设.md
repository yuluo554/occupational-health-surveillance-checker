# 04 模块详设（算法与判定模型）

> 上游：[03-架构与技术选型.md](03-架构与技术选型.md)。本文件定义每个判定模块的**算法、数据结构、边界处置与真值语义**。
> 判定层全部为**纯函数**：`(输入, EffectiveRuleset) → 结果对象`，不读盘不计时。

## 一、领域数据模型（`model.py`）

### 1.1 岗位画像 `PositionProfile`（输入，只读）

```jsonc
{
  "position_id": "POS-001",                // 岗位稳定 ID
  "position_name": "苯罐区操作岗",
  "employer_id": "EMP-SYN-001",
  "exam_date": "2026-09-15",               // ★版本锚定的锚点
  "factors": [
    {
      "factor_code": "SYN_BENZENE",        // 必须是规则包中存在的 code
      "exposure": { "value": "12.5", "unit": "mg/m3" },   // 缺省则触发 input_required 索取
      "years": 6                            // 接触工龄
    }
  ],
  "last_exam_dates": {                     // 时点类型 → 上次检查日期（可缺）
    "periodic": "2025-09-20"
  }
}
```

**字段级校验**：`exam_date` 必须 ISO-8601；`factors[].factor_code` 必须在**锚定版本**的规则包中存在，否则记 `unknown_factor` 原因码（不静默丢弃）；`exposure.value` 用 `Decimal` 解析。

### 1.2 监护档案 `HealthRecord`（输入，只读）

```jsonc
{
  "record_id": "REC-0001",
  "employee_id": "SYN-A-001",              // ★稳定身份键（跨轮对账配对主键）
  "employee_name": "示例人员 A-001",        // 虚构代号，仅呈现
  "position_id": "POS-001",
  "factor_code": "SYN_BENZENE",
  "exam_date": "2026-09-15",
  "exam_type": "periodic",                 // pre_placement | periodic | post_placement | emergency
  "items": ["SYN_ITEM_001", "SYN_ITEM_007"],
  "conclusion_code": "normal",             // 结构化代码，非医学判读文字
  "notified_suspected": false              // 疑似职业病告知标记（仅结构核对）
}
```

### 1.3 结果对象

| 对象 | 关键字段 |
|---|---|
| `PlanResult` | `ruleset_id`、`factor_results[]`（每因素）、`missing_inputs[]`、`trace[]`（溯源行） |
| `FactorPlan` | `factor_code`、`applicable`（三态）、`exams{时点 → {required_items[], supplementary_items[], optional_items[], period}}`、`basis` |
| `CoverageResult` | `record_id`、`verdict`（四态）、`missing_items[]`（含 basis）、`extra_items[]`、`period_verdict`、`findings[]`、`trace[]` |
| `ScanResult` | `items[]`（`kind: ok/failed`）、`stats`（群体统计）、`failed[]`（原因码单列） |
| `ReconcileResult` | `new_missing[]`、`resolved[]`、`persistent[]`、`aux`（新件/消失件） |

## 二、矩阵推导（`engine/matrix.py`）— FR-A1/A2/A3/A4/A5

### 2.1 算法

```
compute_plan(profile, ruleset) -> PlanResult
  ├─ ruleset_id 已在编排层由 exam_date 锚定（version.py）
  ├─ gate = effective_ruleset(ruleset, scope="plan", required_factor_ids={profile 用到的 codes})
  │     └─ 命中 pending → 抛 GateBlocked（退出码 2），错误信息列出未核对的条目坐标
  └─ 对每个 factor：
       ├─ 适用性判定判据 = factor.eligibility
       │    ├─ kind="always"          → applicable = True
       │    ├─ kind="threshold"       → 按 comparator 比较 exposure.value（Decimal 比较）
       │    │    └─ exposure 缺失 且 status≠input_required → 记 missing_inputs
       │    ├─ kind="input_required"  → 记 missing_inputs（**不判 True/False**，交付方给值后重算）
       │    └─ kind="pending"         → 被门控拦住（不进此分支）
       ├─ applicable == False → 输出 applicable=False，四类检查**不产出应检项**（FR-B7 不适用）
       └─ applicable == True  → 对四个时点各取 examinations[时点]
            └─ required_items（判定用）+ supplementary_items + optional_items
```

### 2.2 判定用项目集合的定义（关键口径）

**应检项集 `expected = required_items`**——**只算必检项目**。理由：补充项目（supplementary）的标准表述通常含"必要时/根据具体情况"，属**条件性**项目，纳入判定会把"医生按临床判断未做"误判成缺项（假阳性）。

| 集合 | 是否进 `expected` | 判定产出 |
|---|---|---|
| `required_items` | ✅ 是 | 缺失 → `missing_items` |
| `supplementary_items` | ❌ 否 | 缺失 → 不报（报告呈现为"可选项"） |
| `optional_items` | ❌ 否 | 缺失 → 不报 |

**推论的诚实留档**：本口径意味着工具**不做**"该做补充检查没做"的判定，这是**有意的边界**（补充项目的条件由临床判断，不在确定性规则能力内）。README 限制节必须明示此点，**不得让读者以为工具覆盖了补充项目合规**。

### 2.3 溯源行（FR-A4）

每条产出（应检项 / 周期 / 适用性结论）必须产出一行 `trace`：

```
{ "target": "POS-001/SYN_BENZENE/periodic/SYN_ITEM_001",
  "value": "required",
  "basis": "GBZ 188—2025 第 5.1.0 节",
  "source": {"doc": "...", "clause": "...", "url": "...", "fetched": "..."} }
```

**硬断言**（导出前）：`len(trace) >= len(明细行) + len(因素行)`，且每条 trace 的 `basis` 非空。不满足即**拒导**（不留半溯源报告）。

## 三、覆盖度核查（`engine/coverage.py`）— FR-B1/B2/B3/B5/B7

### 3.1 四态判定模型

```
verdict(record, plan_for_record) ->
  ├─ 1) 适用性：plan.applicable == False          → "not_applicable"（"不适用"，**不计违规**）
  ├─ 2) 时点齐备性：
  │       expected = plan.exams[record.exam_type].required_items
  │       actual   = normalize(record.items)        # 别名归一（见 3.3）
  │       missing  = expected - actual
  │       ├─ missing 为空     → 继续 3)
  │       └─ missing 非空     → 记录 missing_items（每项挂 basis）
  ├─ 3) 周期合规：period_verdict = judge_period(...)（见 §四）
  └─ 定级：
        missing 为空 且 period == "compliant"          → "compliant"      （符合）
        missing 非空 或 period == "overdue"            → "partial"        （部分符合）
        missing 覆盖全部必检项（expected ⊆ missing）    → "non_compliant"  （不符合）
        任一步骤为 unknown（如结论项未能核对）          → 不降级为 compliant，记 unknown 并计入"待人工确认"
```

### 3.2 定级边界（写死，避免漂移）

| 情形 | verdict | 退出码贡献 |
|---|---|---|
| 应检项全齐 + 周期合规 | `compliant` | 无 |
| 缺 1 项以必检项，不超期 | `partial` | **1** |
| 必检项**一项未做**（`expected ⊆ missing` 且 `expected` 非空） | `non_compliant` | **1** |
| 周期超期（无论有无缺项） | `partial` 或 `non_compliant`（见上） | **1** |
| 岗位危害因素不适用该人员 | `not_applicable` | 无 |
| 危害因素代码不识别 / 缺必填字段 | **不产出 verdict**，记 `failed` + 原因码 | 无（见 03 §七纪律 1） |
| 别名归一不成立（项目名无法映射到规范代码） | 该**单项**降级 `warning`，不硬判缺失 | 无 |

**`warning` 而非 `fail` 的理由**：项目名称写法差异（如"血常规"vs"血细胞分析"）是**表述问题**而非事实缺失，硬判会造成假阳性。误报对照集（FR-E4）专门守这条。

### 3.3 别名归一（FR-B5）

```jsonc
// 规则包内 aliases 段（M1 建）
{ "alias_map": { "血细胞分析": "SYN_ITEM_001", "血常规": "SYN_ITEM_001" },
  "status": "pending" }
```

- 归一顺序：精确 code 命中 → 别名表命中 → **归一无结果则记 `unmapped_item` 并降级 warning**。
- `alias_map` 本身也挂 `status`；**pending 时归一路径整体禁用**，此时所有非精确命中的实检项一律记 `unmapped_item` warning——**不猜**。
- **禁止模糊匹配**（编辑距离/子串包含）：会制造假阴性。归一必须是显式表。

## 四、周期判定（`engine/period.py`）— FR-B4

```
judge_period(period_rule, last_exam_date, current_exam_date) ->
  ├─ period_rule.kind == "pending"        → 门控拦截（退出码 2）
  ├─ period_rule.kind == "input_required" → 记 missing_inputs（不判定）
  ├─ period_rule.kind == "none"           → "not_applicable"（该因素无周期要求）
  └─ period_rule.kind == "months":
        due = last_exam_date + relativedelta(months=value)    # 月加法：日历月，非 30 天
        ├─ current < due          → "compliant"
        ├─ current == due         → "due"        （恰好到期，**合规**：到期当日检查即合规）
        └─ current > due          → "overdue"
```

**月加法的确定性实现（不引 dateutil）**：自写 `add_months(d, n)`——先加整年再加月，**月末夹取**（`1/31 + 1 month = 2/28 或 2/29`，按目标月实际天数 clamp）。这是**必须写测试的边界**（1/31、2/29、12/31 跨年）。

**边界口径写死**：
- 到期当日检查 = **合规**（`due` 计入合规，不报超期）。
- 判定基准是 `current_exam_date` 与 `last_exam_date`（**不做"今天"判定**——用"今天"会让结果随时间漂移，破坏可复现性）。
- 首次检查（无 `last_exam_date`）→ `period_verdict = "no_baseline"`，**不报超期**，报告单列。

## 五、批量扫描（`engine/scan.py`）— FR-D1/D2/D5

### 5.1 分派点唯一

```
scan_directory(dir, policy) -> ScanResult
  └─ 对每份档案调用 **同一个** engine.check_record()（单件通路也走它）
```

**纪律**：`check`（单件）与 `scan`（批量）**必须共用同一分派点**。两条通路各写一套判定 → 必然对同一文件给出不同结论（最隐蔽的口径漂移）。

### 5.2 失败隔离与原因码

| 原因码 | 触发 |
|---|---|
| `read_error` | 读盘失败 |
| `bad_json` | JSON 解析失败 |
| `schema_invalid` | 缺必填字段 / 类型错 |
| `unknown_factor` | `factor_code` 不在锚定版本规则包中 |
| `unknown_exam_type` | 时点类型不在四类内 |
| `container_too_large` | 超过 `max_bytes`（安全阀，**不整体读入**） |
| `gate_blocked` | 门控拦截（pending 进入路径） |
| `missing_input` | `input_required` 未提供 |

**异常经捕获**，单件失败 → `kind="failed"` + 原因码，**整批继续**；失败件在结果与报告中**单列**，绝不静默吞掉。`scan_error` 类**不改变退出码**。

### 5.3 群体统计（FR-D4）

按 `factor_code` / `position_id` 汇总：应检人数、实检人数、缺检人数、超期人数、不适用人数、失败件数。统计由明细**逐项可复算**（基准断言：`sum(明细) == 统计`）。

## 六、跨轮对账（`engine/reconcile.py`）— FR-D3

```
compare_rounds(current_scan, baseline_scan) ->
  key = ("employee:<employee_id>", "<factor_code>/<exam_type>/<item_code>")
  三主集 + 两辅助集：
    new_missing  = 本轮的缺项 ∩ 不在上轮缺项
    resolved     = 上轮的缺项 ∩ 不在本轮缺项
    persistent   = 两轮都缺
    aux.new_records / aux.gone_records           # 按 employee_id 的件级增删
```

**三条硬纪律**：
1. **配对主键 = 稳定身份键**（`employee_id` + 缺项坐标），**不是内容指纹**。用内容指纹配对时"已补齐"必然内容变了 → 永远配不上 → **`resolved` 永远检不出**。
2. 内容变化**另立** `content_changed` 标记，不让它退化成"新增 + 移除"。
3. 对账口径**单一实现源**（`engine/reconcile.py` 的函数供测试与基准共用），否则"基准说达标、测试说不过"的双口径漂移。

## 七、版本对照（`engine/` 的 compare 通路）— FR-C3

```
compare_rulesets(rs_a, rs_b) -> DiffReport
  ├─ 仅需结构字段（factor_code / factor_name / examinations 键集 / period.kind）
  │    → 门控 scope="compare"，**不要求项目明细 verified**
  ├─ 危害因素覆盖差异：新增（B 有 A 无）/ 删除（A 有 B 无）
  ├─ 检查时点差异：某因素某时点的存在性变化
  ├─ 检查项目构成差异：required_items 的 code 集合差异
  ├─ 选检项目调整：optional_items 由非空变空（2025 版删除选检）
  └─ 每条差异挂 A/B 两侧的 basis（可追到前言/节次）
```

**M0 骨架**：`compare` 只出结构骨架（计数与键集比较），条目级差异待 M1 规则入库后生效；**未核对的差异条目不得以确定语气呈现**——M0 期报告须写"规则包条目为 pending，本差异仅为结构对照"。

## 八、报告结构（`report/`）— FR-F2/F3/F4/F5/F7/F8

### 8.1 单一渲染源（关键）

```python
def report_sections(model) -> list[Section]:   # ★唯一章节结构函数
    ...                                         # Section(title, tables, paragraphs, notes)
def render_markdown(sections) -> str
def render_xlsx(sections) -> bytes
```

Markdown 与 XLSX **都消费同一个 `report_sections()`**——于是"两格式内容一致"是**结构性质**（改一处两者同变），不是人工比对出来的。配套测试：从两种产物抽出内容做**逐项对等断言**（不是断言"都调了同一个函数"这种字面声明）。

### 8.2 章节清单

| # | 章节 | 内容 | 未启用时 |
|---|---|---|---|
| §0 | 报告头 | **规则包坐标**（依据版本 + 版本号 + 生成时间）+ 免责声明 | 必出 |
| §1 | 输入事实 | 岗位/档案摘要、条数、数据指纹 | 必出 |
| §2 | 岗位危害因素画像 | 因素 × 适用性 × 接触水平 | 必出 |
| §3 | 应检清单与条款依据 | 四时点 × 项目 × basis + trace 行 | 必出 |
| §4 | 覆盖核查明细 | 逐人 verdict + 缺项 + 别名降级警告 | 必出 |
| §5 | 周期合规 | 上次检查/到期日/判定 + `no_baseline` 单列 | 必出 |
| §6 | 群体统计 | 按因素/岗位汇总 | 批量通路时出 |
| §7 | 跨轮对账 | 三主集 + 两辅助集 | 无 baseline → **写"本次导出未启用跨轮对账（用 --baseline 启用）"** |
| §8 | 整改台账 | 缺项 → 责任建议（措辞为"建议"） | 必出 |
| §9 | 参数来源块 | 规则包出处（发布机关/文号/URL/抓取日期） | 必出 |
| §10 | 失败件清单 | 原因码单列 | 无失败件 → "本次无失败件"（显式写，不留空） |
| §11 | 免责声明 | 全文 | 必出 |

**"未启用"必须显式写出**——"没查"与"查了没问题"是两种截然不同的结论，留空会被误读成后者。

### 8.3 无外链硬断言（FR-F5）

- Markdown：正文无 `http://`/`https://`；URL 只出现在 §9 参数来源块，且以**纯文本**形式（非 Markdown 链接语法）。
- XLSX：无 `TargetMode="External"`、无 `w:hyperlink`；`.rels` 里 Relationship `Type` 属性本身是 http URI（OOXML 规范如此）→ **不能对 .rels 全文做 http 子串扫描**，断言须按上述三条。
- 断网可开：两种产物均无外部依赖。

### 8.4 字节可复现（FR-F6）

| 产物 | 措施 | 验收 |
|---|---|---|
| Markdown | `write_bytes` + 显式 `\n`；生成时间由调用方注入 | 两次导出 sha256 一致 |
| XLSX | `ZIP_STORED` + `create_system=0` + `date_time=(1980,1,1,0,0,0)` + 固定 `external_attr`；文档属性无 `created`/`modified` 时间戳 | **两次导出 sha256 一致（须实测背书，不得只写在计划里）** |

### 8.5 证据链（FR-F1/F2）

```jsonc
// evidence.json
{ "ruleset": {"ruleset_id": "...", "sha256": "..."},
  "inputs": [{"path": "…", "sha256": "…"}],     // 本地文件引用与指纹
  "outputs": [{"path": "…", "sha256": "…"}],    // ★报告产物自身也挂指纹
  "generated_at": null,                          // 不写时间 → 保持字节可复现
  "verified_at_note": "生成时间不写入本文件以保全逐字节可复现" }
```

**"报告被改动即可检出"**：`outputs[]` 含报告自身 sha256 → 改动报告即与 `evidence.json` 不符。

## 九、基准设计（`benchmark/`）— FR-E1–E6

### 9.1 四类套件

| 套件 | 驱动方式 | 判据 |
|---|---|---|
| `matrix` | 样本驱动（真值库全量重算）+ **规则驱动**（从规则表推导端点，±邻域断言） | 正确率 ≥ manifest 门槛 |
| `coverage` | 样本驱动（合成档案植入真值） | 判定正确率 = 100% |
| `compare` | 双版本对照（同一岗位两版期望差异） | 一致率 = 100% |
| `false_positive` | **只读**真值库的"应零命中"声明，不自选考卷 | 违规数 = 0 |

### 9.2 样本驱动 vs 规则驱动（覆盖面的关键区分）

- **样本驱动**证明"引擎在这些样本上对"，但**样本没覆盖的端点它证明不了**。
- **规则驱动**不读真值库，只从规则表推导切换端点做断言，证明"引擎在**所有**有限端点上对"。
- **判据口诀**："这个基准的分母，是否依赖真值库恰好覆盖了某个端点？"依赖 → 是样本驱动，须补一条规则驱动的。

### 9.3 可证伪探活（FR-E5）

每套件配一个**注入缺陷**的探活测试：故意坏掉一个引用/期望值 → **断言基准必须报未达标**。不配探活的"基准全绿"可能只是"基准什么都没查"。

### 9.4 门槛与退出码

- 门槛从 `manifest.benchmark_thresholds` 读；**缺失即退出码 2**，不得回落代码默认值。
- `--only <suite>` 传未知名 → **退出码 2**（否则"跑了个不存在的基准"会被读成成功）。
- `--suite` 部分运行时不判定未测指标（否则会把"没测"误报成"未达标"，把"未知"当"失败"）。
- 退出码：0 达标 / 1 未达标或计算非法 / 2 输入、坐标或用例名错误。

## 十、GUI 分层（M5）— FR-G2/G3

| 层 | 文件 | 约束 |
|---|---|---|
| 编排层 | `engine/pipeline.py` 公开函数组 | GUI 与 CLI **唯一**取数入口 |
| 服务层 | `gui/service.py` | GUI 唯一允许 import 引擎的模块 |
| 表现层 | `gui/pages/*.py` | 只渲染；**AST 三条守门**：不 import 规则层 + 无 `BinOp` 算术 + 无政策数值字面量 |

**三条齐上的理由**：只断言"不 import 规则层"会漏掉两种绕过——① 在界面层直接算（`value * 2`）；② 把周期数值写进界面。三条合起来才等于"界面只做展示与转发"。

**行为等价验收（三方对账）**：CLI stdout 的结论 == 直接调 pipeline 的字段 == 报告章节里的内容；且同一输入两次调用逐字段一致。**不是**断言"都调了同一个函数"这种字面声明。
